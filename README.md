# Customer Churn & Retention Analytics

A business-analyst project answering one question: **which customer segments
are churning, why, and where should limited retention effort go first?**

Built on 5,000 synthetic SaaS customers: cohort retention analysis, churn
drivers, LTV vs CAC, month-over-month churn trend, and a chi-square
significance test — every number below comes from a real run of
`python/churn_analysis.py` (run on 2026-09-26).

## Why, how, what

**Why** — churn is the silent killer of subscription revenue, but retention
teams can't call everyone. Without knowing *who* churns and *why*, retention
effort spreads thin and misses the segments where it would pay off most.

**How** — (1) Generate 5,000 labelled customers with realistic churn patterns.
(2) Run EDA and engineer behavioural features (tenure, ticket intensity,
login recency). (3) Measure retention with cohort curves, compare churn
across plans and segments with 95% confidence intervals, test whether
segment differences are statistically significant (chi-square).
(4) Compute LTV by segment and compare against acquisition cost.
(5) Turn the findings into a prioritised retention plan.

**What** — a reproducible churn-analysis toolkit: labelled dataset, one
script that runs the full analysis, six charts, a SQL query pack
(`sql/queries.sql`) reproducing every headline KPI, and a written retention
recommendation backed by measured numbers.

## Analytics type

| Type | How this project uses it |
|---|---|
| **Diagnostic** (primary) | Explains *why* churn happens: high support tickets, short tenure, long login recency, Basic plans, Startup segment. |
| **Prescriptive** | Tells the business *where to act first*: Startup + Basic customers (29.3% churn, 3.0x LTV:CAC, 46% of the base). |
| **Predictive** | Churn-risk signals: dormant recency (31d+) and high ticket volume flag at-risk customers *before* they leave. |
| **Descriptive** | Cohort heatmaps, churn-rate bars and the MoM trend describe *what* churn looks like across the business. |

## SQL analysis layer

Every headline KPI is also computed directly in SQL — the same aggregations
an analyst would run against a production customers table.
[`sql/queries.sql`](sql/queries.sql) (MySQL-compatible) reproduces, all exact:

- **overall churn** — 22.9% across 5,000 customers
- **churn by segment** — Startup 29.3%, SMB 20.8%, Mid-market 11.0%
- **churn by plan** — Basic 31.5%, Pro 17.4%, Enterprise 8.0%
- **ticket intensity** — churned 2.2 vs retained 1.5 support tickets
- **login recency** — churned 29.5 vs retained 4.0 dormant days
- **high-ticket churn** — 36.2% for customers with 4+ tickets vs 21.2% otherwise

SQL handles the extraction, aggregation, and KPI computation; Python handles
the statistical testing (chi-square, confidence intervals), charts, and the
retention write-up.

## Dataset

`data/customers.csv` — 5,000 customers, 12 signup cohorts (Oct 2025 – Aug 2026),
generated by `data/generate_churn_data.py` (seed = 42, fully reproducible).

| Column | Description |
|---|---|
| customer_id | Unique id (CUST-00001 …) |
| signup_date | Cohort assignment |
| plan | Basic / Pro / Enterprise |
| segment | Startup / SMB / Mid-market |
| monthly_revenue | MRR in ₹ (plan-dependent) |
| tenure_months | Months since signup |
| support_tickets_last_90d | Ticket count |
| days_since_last_login | Login recency |
| churned | Ground-truth label (1 = churned) |
| churn_date | Date of churn (empty if retained) |

> All data is synthetic. No real customers are involved.

## Methods

- **EDA** — customer mix by plan/segment, overall churn rate.
- **Feature engineering** — derived `active_months`, `tickets_per_month`,
  `is_high_ticket` (≥4 tickets), `recency_bucket` (active/lapsing/dormant),
  `revenue_tier` from the raw columns.
- **Cohort analysis** — retention = % of a signup cohort still active *k*
  months after signup; unobservable cells masked.
- **Confidence intervals** — 95% normal-approximation CIs on every churn rate.
- **Chi-square test** — is the segment × churn association statistically
  significant, or plausibly random noise?
- **LTV** = avg monthly revenue × avg tenure, per segment.
  **CAC is ASSUMED** (Startup ₹6,000 · SMB ₹18,000 · Mid-market ₹60,000) —
  clearly labelled everywhere; the ratios demonstrate the *method*, not real
  unit economics.
- **MoM churn** — churned in month ÷ active base at month start.

## Results

All figures are the actual output of `python/churn_analysis.py`:

**Headline:** overall churn rate **22.9%** (95% CI 21.7% – 24.0%) across 5,000 customers.

| Plan | Churn | 95% CI |
|---|---|---|
| Basic | **31.5%** | 29.7% – 33.4% |
| Pro | 17.4% | 15.6% – 19.2% |
| Enterprise | 8.0% | 6.1% – 9.9% |

| Segment | Churn | 95% CI |
|---|---|---|
| Startup | **29.3%** | 27.5% – 31.2% |
| SMB | 20.8% | 18.9% – 22.7% |
| Mid-market | 11.0% | 9.0% – 12.9% |

- **Chi-square (segment vs churn):** χ² = 134.9, p = 5.07e-30 — far below
  0.05, so the segment differences are statistically significant, not noise.
- **Churn drivers** (churned vs retained): tenure 5.2 vs 6.3 months; support
  tickets 2.2 vs 1.5 per 90 days; days since login 29.5 vs 4.0. High-ticket
  customers (≥4 tickets) churn at **36.2%** vs 21.2% for the rest.
- **Recency buckets:** active (0–7d) 3.1% churn · lapsing (8–30d) 58.0% ·
  dormant (31d+) 99.8%. (Honest note: in this synthetic setup recency was
  generated as a *consequence* of churn, so treat it as a lagging signal
  here; in production it is a leading one.)
- **Cohorts:** average month-3 retention 87.8%; best cohort 2025-10 (95.0%),
  worst 2026-05 (75.5%).
- **LTV:CAC:** Startup ₹17,959 → **3.0x** · SMB ₹30,971 → 1.7x ·
  Mid-market ₹59,130 → 1.0x (CAC assumed — see Methods).
- **MoM churn trend:** 0.9% – 6.6% per month; latest (2026-08) 6.6%.

### Retention recommendation (prescriptive)

1. **Start with Startup + Basic customers** — 29.3% churn, 46% of the base,
   and the best LTV:CAC (3.0x): the biggest lever per rupee of effort.
2. **Trigger proactive outreach at ≥4 support tickets** — those customers
   churn at 36.2%; a ticket is a cry for help before it becomes a cancellation.
3. **Win-back campaign for dormant (31d+) logins** — the strongest
   churn-risk signal in the data.
4. Mid-market churn is low (11.0%) but watch the assumed CAC: at ~1.0x
   LTV:CAC there is little room for expensive retention plays there.

## Limitations

- Synthetic data with baked-in patterns — the *methods* transfer to real
  data; the specific numbers do not.
- CAC is an assumed input, not a measured one — LTV:CAC ratios illustrate
  the framework only.
- Login recency here is a lagging (post-churn) signal by construction; treat
  the dormant-bucket finding as a signal demo, not a causal claim.
